# 1.0.0-rc.1

[All versions](README.md)

The release candidate for 1.0. From here the package follows semantic versioning over its
published interface: a minor or patch version keeps every class, resource key and include path an
app names, and only a major version breaks one. Since 0.33.0 a variant switch is fast again; the
styles, keys and classes are 0.33.0's.

## What changed

- **Semantic versioning over the published interface.** [Compatibility](../compatibility.md)
  lists what an app can rely on within a major version, the include paths, classes, resource keys
  and `FiliThemeVariants`, each pinned by a test, and what may change in a minor version. A key
  that has to go is kept as an alias until the next major version.
- **Fixes go into the newest 1.x.** [The security policy](../../SECURITY.md) says which versions
  get fixes: the newest 1.x release, which an app can move to without a change. Versions before
  1.0 and prereleases get none of their own.
- **Switching variant is fast again.** Since 0.32.0 every variant has brushes of its own, so a
  window or `ThemeVariantScope` paints in its own variant; but a switch of the application's
  variant handed every control a new brush in every brush property, and took up to three times as
  long. A lookup for the application's own variant now finds one brush per key that follows it,
  so a switch recolours the brushes a control has, as before 0.32.0, while a window or scope with
  another variant still paints in that one. On the benchmark screen a switch takes 40% less
  time than in 0.33.0, and allocates a thirteenth of what it did; building a screen costs what it
  did.

## Upgrading from 0.33.0 to 1.0.0-rc.1

Nothing has to change. A brush looked up in code for the application's variant is now the same
object before and after a switch, recoloured, where 0.32.0 and 0.33.0 returned a different one
per variant.
